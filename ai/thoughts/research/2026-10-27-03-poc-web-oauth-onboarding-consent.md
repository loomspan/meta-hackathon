### The consent flow as Supabase actually requires it (docs + source, fetched 2026-10-27)

Sources: [Getting Started with OAuth 2.1 Server](https://supabase.com/docs/guides/auth/oauth-server/getting-started), [OAuth 2.1 Flows](https://supabase.com/docs/guides/auth/oauth-server/oauth-flows), [Deploy MCP servers](https://supabase.com/docs/guides/ai-tools/byo-mcp), and `supabase-js` master `GoTrueClient.ts` / `lib/types.ts` (URLs: `https://raw.githubusercontent.com/supabase/supabase-js/master/packages/core/auth-js/src/GoTrueClient.ts`, `.../src/lib/types.ts`).

1. **Composition of the consent URL.** "The authorization path is combined with your Site URL … to create the full authorization endpoint URL" (getting-started). With ticket 3's settings that is `https://loomspan.ai` + `/poc/oauth/consent` = `https://loomspan.ai/poc/oauth/consent`, matching ticket `:11,18`.
2. **Arrival.** The MCP/OAuth client redirects the user to `https://<project-ref>.supabase.co/auth/v1/oauth/authorize` with `response_type=code`, `client_id`, `redirect_uri` (must exactly match a registered URI), `code_challenge`, `code_challenge_method=S256` (or `plain`), and optional `state` (recommended), `scope` (space-separated; default `email`), `nonce`. Supabase Auth validates the parameters, then redirects to the configured authorization path **with an `authorization_id` query parameter** (oauth-flows step 3; getting-started "Build your authorization UI" steps 1–5). This is precisely the ticket's premise (`ticket:15`).
3. **Sign-in preservation.** The documented pattern is: extract `authorization_id`; if the user is not signed in, redirect to a sign-in page **preserving the `authorization_id`** (docs examples use `/login?redirect=/oauth/consent?authorization_id=${authorizationId}` in both Next.js and React SPA forms), then return to the consent path with the same `authorization_id` after sign-in. The docs do not mandate a separate login route — they mandate that the id survives whatever sign-in step the frontend uses. In `supabase-js`, the three consent methods each run inside `_useSession(...)` and return an `AuthSessionMissingError` result (`{ data: null, error }`) when there is no session (`GoTrueClient.ts` `_getAuthorizationDetails` / `_approveAuthorization` / `_denyAuthorization`), so the page must establish a session (e.g. `supabase.auth.signInWithPassword(...)` for the dashboard-created test users, or an existing persisted session detected via `getUser()`/`getSession()`) before calling them. The React SPA example in getting-started checks `supabase.auth.getUser()` first and navigates to login preserving the id when absent.
4. **Authorization details.** `supabase.auth.oauth.getAuthorizationDetails(authorizationId: string): Promise<AuthOAuthAuthorizationDetailsResponse>` (public namespace assigned in `GoTrueClient.ts` constructor: `this.oauth = { getAuthorizationDetails, approveAuthorization, denyAuthorization, listGrants, revokeGrant }`, typed as `AuthOAuthServerApi` on the client). It performs `GET {authUrl}/oauth/authorizations/{authorizationId}` with the signed-in user's access token as the JWT. The success type is a union (`lib/types.ts`):
   - `OAuthAuthorizationDetails` — `{ authorization_id: string, redirect_uri: string, client: { id: string (UUID), name: string, uri: string, logo_uri: string }, user: { id: string, email: string }, scope: string }`. `scope` is singular, a space-separated string such as `"openid email profile"`; the ticket's "requesting client and requested access" (`ticket:16,29`) map to `client.name` (plus `client.uri`/`logo_uri`/`redirect_uri` if shown) and `scope.split(' ')`.
   - `OAuthRedirect` — `{ redirect_url: string }` only. Returned when the user has **previously consented** to these scopes (auto-approved): per the source doc-comment, "If the response includes only a redirect_url field, it means consent was already given — the caller should handle the redirect manually if needed", and the docs examples branch on `if (!('authorization_id' in authDetails)) redirect(authDetails.redirect_url)`. A consent page that unconditionally renders `data.client.name` will break on repeat connections; this is a behavior inside the ticket's flow, not a different flow.
5. **Approve / deny.** `approveAuthorization(authorizationId: string, options?: { skipBrowserRedirect?: boolean }): Promise<AuthOAuthConsentResponse>` and `denyAuthorization(...)` with the identical signature. Both `POST {authUrl}/oauth/authorizations/{authorizationId}/consent` with body `{ action: 'approve' }` or `{ action: 'deny' }` and the user's JWT; the response is `OAuthRedirect` (`{ redirect_url }`), where approval's URL carries `code` + `state` to the client's `redirect_uri` and denial's carries `error=access_denied&error_description=...&state=...` (oauth-flows step 4). **Browser behavior:** unless `skipBrowserRedirect: true` is passed, the library itself calls `window.location.assign(response.data.redirect_url)` in a browser. The docs' SPA example instead passes no options and then also sets `window.location.href = data.redirect_url` after the call; either way the observable contract is that the browser ends at `redirect_url`. Denial therefore produces an OAuth error redirect, not a token — consistent with ticket `:22` (a denied request must yield no usable token); ticket 3's denial test still has to evidence that no authenticated tool call follows.
6. **Token exchange (client side, for the reference flow).** `POST https://<project-ref>.supabase.co/auth/v1/oauth/token`, `Content-Type: application/x-www-form-urlencoded`, `grant_type=authorization_code`, `code`, `redirect_uri`, `code_verifier`, plus client authentication by `token_endpoint_auth_method`: `none` (public clients; only `client_id` in body), `client_secret_basic` (default for confidential clients), or `client_secret_post`. Authorization codes are short-lived (10 minutes), single-use, and PKCE-bound (oauth-flows steps 4–5). Supported grants are only `authorization_code` and `refresh_token`; scopes supported are `openid profile email phone offline_access`, default `email`, custom scopes not supported, and "All OAuth access tokens have full access to user data (same as regular session tokens), with the addition of the `client_id` claim" (oauth-flows, Available scopes) — i.e. membership enforcement remains the MCP function's job, exactly as implemented in ticket 2.

### Discovery and DCR endpoints (reference-flow chain)

- Hosted discovery document, fetched read-only during this research from `https://yjrwyfkybszlpufsflan.supabase.co/.well-known/oauth-authorization-server/auth/v1` (HTTP 200): `issuer` `https://yjrwyfkybszlpufsflan.supabase.co/auth/v1`; `authorization_endpoint` `.../auth/v1/oauth/authorize`; `token_endpoint` `.../auth/v1/oauth/token`; `jwks_uri` `.../auth/v1/.well-known/jwks.json`; `userinfo_endpoint` `.../auth/v1/oauth/userinfo`; `registration_endpoint` `.../auth/v1/oauth/clients/register` (DCR); `scopes_supported` `[openid, profile, email, phone, offline_access]`; `response_types_supported` `[code]`; `grant_types_supported` `[authorization_code, refresh_token]`; `code_challenge_methods_supported` `[S256, plain]`; `token_endpoint_auth_methods_supported` `[client_secret_basic, client_secret_post, none]`; `id_token_signing_alg_values_supported` `[RS256, HS256, ES256]`. This corroborates `poc/README.md:24` ("advertises authorization, token, and dynamic client registration endpoints"). OIDC discovery is also published at `.../auth/v1/.well-known/openid-configuration` per getting-started's endpoint table (not separately fetched).
- MCP protected-resource discovery: the Edge Function composes `pipeline([withOAuthProtectedResource(), withSupabase({ auth: "user" })], ...)` (`poc/mcp-server/supabase/functions/mcp/index.ts:38-39`). Per the BYO-MCP guide, `withOAuthProtectedResource()` serves the OAuth Protected Resource Metadata document and adds the `WWW-Authenticate` challenge to 401s so clients can find the authorization server; the guide's example metadata URL is `<function-base>/oauth-protected-resource` returning `authorization_servers: ["<origin>/auth/v1"]`. The reference-flow chain is therefore: unauthenticated MCP POST → 401 + `WWW-Authenticate` → protected-resource metadata → authorization-server discovery (above) → DCR `POST .../auth/v1/oauth/clients/register` → authorize redirect → consent page → token exchange → authenticated MCP `initialize` + `tools/call`.
- Already proven vs. not: the 401 challenge and authenticated tool calls are proven hosted with password-grant tokens (`poc/README.md:135`; `poc/mcp-server/tests/hosted-acceptance.mjs:26-36,95-97`). The DCR → authorize → consent → code-exchange leg has never been executed against this project in any repo artifact; that is ticket `:20`'s reference flow. `poc/README.md:121` is explicit that ticket 2's direct-token verification is not the companion OAuth proof.

## Dependencies and Operational Constraints

- **Service-role key leakage risk (concrete paths).** The service-role key exists in exactly one legitimate place: the Edge Function runtime env, read at `index.ts:26` (`Deno.env.get("SUPABASE_SERVICE_ROLE_KEY")`) to build the privileged repo (`data.ts`) that bypasses RLS (all six fixture tables have RLS enabled with no policies — see ticket-2 research). Leakage routes relevant to ticket 3: (1) copying any server-side snippet, `.env` file, or config into `poc/web/` or the deployed Pages output — the secret-scan test already walks all of `poc/` and flags `service[_-]?role … eyJ` and JWT-shaped strings, but it scans this repo, not the separate `loomspan.ai` repo's deployed output, which ticket `:31` separately requires to be clean; (2) the public anon/publishable key is safe to embed (it is the `apikey` header credential in `hosted-acceptance.mjs:29` and the intended browser key per ticket `:14`), but because OAuth access tokens "have full access to user data (same as regular session tokens)" (oauth-flows), the consent page's protection is the signed-in session check in the `supabase-js` methods themselves (session-missing error), not key secrecy; (3) evidence/recording hygiene — `poc/README.md:32,121` and ticket `:21,32` forbid recording tokens, codes, or credentials, so reference-flow logs must redact the authorization `code`, tokens, and `code_verifier` while retaining step/status evidence. - **Beta surface.** OAuth 2.1 server is beta, available on all plans, no separate charge (getting-started); users signing in through it count toward MAU. Custom scopes are not supported (oauth-flows) — the consent page can only display the standard scopes the client requested.
- **Dashboard-only Auth changes.** Site URL and Authorization Path are changed in the dashboard; `supabase config push` must never be run (`poc/README.md:117`). Changing the Site URL to `https://loomspan.ai` also affects any other Auth redirect that relied on `http://localhost:3000`; no repo artifact records another consumer of the current Site URL.

Denial/approval tests must account for grant state: a user who already granted a client may not see a consent decision at all until the grant is revoked (`supabase.auth.oauth.listGrants` / `revokeGrant` also exist on the same namespace).
- **Cross-repo manual deployment.** No automation links this repo to `loomspan.ai`; deployment, live-URL verification, and SPA-fallback checking are human/pipeline actions in the other repo, whose location and tooling are unknown here (see Open Questions).
