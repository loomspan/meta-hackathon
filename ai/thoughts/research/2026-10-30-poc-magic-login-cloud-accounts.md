# Magic Login and Cloud Internal Accounts Research

## Research Question

For ticket `2026-10-30-poc-magic-login-cloud-accounts`, what does the checked-out repository establish about: (a) the current consent-page sign-in and how the pending OAuth authorization request survives it; (b) how the MCP server currently identifies and authorizes callers; (c) the fixture schema, membership, seeded data, and tool-call log that an internal-account model would touch; (d) what test coverage exists today and what ticket-required coverage is absent; and (e) which ticket requirements can be executed from this checkout versus which depend on the Supabase dashboard, the separate `loomspan.ai` site repository, or a developer-supplied mailbox through the execution environment?

This research describes current behavior only. It does not propose an implementation.

## Summary

The POC today proves password sign-in with synthetic users and authorizes tools by raw Supabase Auth user ID. The consent page offers only email + password ([poc/web/oauth/consent.html](/C:/opendev/code/meta-hackathon/poc/web/oauth/consent.html:16), [poc/web/assets/consent.js](/C:/opendev/code/meta-hackathon/poc/web/assets/consent.js:68)); no email-code (OTP) API appears anywhere in the repository. The MCP entry point resolves only the Supabase user `id` ([poc/mcp-server/supabase/functions/mcp/index.ts](/C:/opendev/code/meta-hackathon/poc/mcp-server/supabase/functions/mcp/index.ts:40)) and passes it to all three tool handlers; membership checks query `poc_app_memberships` by that UUID ([poc/mcp-server/supabase/functions/mcp/data.ts](/C:/opendev/code/meta-hackathon/poc/mcp-server/supabase/functions/mcp/data.ts:21)). There is no accounts table, no email column, and no email-based resolution anywhere in the schema, server, or web code.

The ticket's required behaviors therefore have no current counterpart: first-sign-in account creation, normalized-email matching (trim + lowercase only), concurrent-first-login uniqueness, authorization by internal account ID, and owner-membership carry-over onto a real mailbox account. The preserved parts are equally concrete: the three tool contracts and error taxonomy in [poc/mcp-server/supabase/functions/mcp/core.ts](/C:/opendev/code/meta-hackathon/poc/mcp-server/supabase/functions/mcp/core.ts:227), the grocery fixture (Oats/2, Apples/4, Milk/1), and the consent page's same-tab, no-navigation sign-in shape that keeps `authorization_id` alive across sign-in.

Three live/external constraints bound what this checkout can do (see Dependencies and Operational Constraints): Supabase Auth settings are dashboard-only and local `config.toml` must never be pushed; the deployed consent page lives in the separate site repository `C:\opendev\code\loomspan-website` (`public/poc/`), reachable on this machine but a different repository; and the designated owner mailbox is supplied only via the execution environment and must never be written to the repository — no such address exists in this checkout and none was sought.

Verified baseline at research time: all six safe Node suites pass 35/35 and the Deno core suite passes 8/8 (commands in Existing Tests and Fixtures). No test today covers OTP sign-in, account creation, email normalization, concurrent resolution, or internal-account authorization.

- Arrival: `parseAuthorizationId(window.location.search)` extracts the `authorization_id` query parameter ([poc/web/assets/consent-core.mjs](/C:/opendev/code/meta-hackathon/poc/web/assets/consent-core.mjs:4), [poc/web/assets/consent.js](/C:/opendev/code/meta-hackathon/poc/web/assets/consent.js:16)). - Session check: `supabase.auth.getSession()`; with a session the page loads authorization details, otherwise it shows the sign-in form ([poc/web/assets/consent.js](/C:/opendev/code/meta-hackathon/poc/web/assets/consent.js:102)).
- Sign-in today is password-only: the form is email + password ([poc/web/oauth/consent.html](/C:/opendev/code/meta-hackathon/poc/web/oauth/consent.html:19)) and submits via `supabase.auth.signInWithPassword(credentials)`, where the form field names are the supabase-js credential keys ([poc/web/assets/consent.js](/C:/opendev/code/meta-hackathon/poc/web/assets/consent.js:68)). On failure the page shows a fixed friendly message and clears the password field; on success it calls `loadDetails()` with no navigation, so the pending `authorization_id` (still in the URL and in memory) survives sign-in in the same tab. This same-tab, no-navigation property is the existing behavior the ticket's email-code requirement ("sign-in happens in the same browser tab as the authorization request") depends on.
- No OTP surface exists: a repository search for `signInWithOtp` / `verifyOtp` / OTP terminology finds no occurrence in `poc/` source. The only sign-in call in the repo is `signInWithPassword` ([poc/web/assets/consent.js](/C:/opendev/code/meta-hackathon/poc/web/assets/consent.js:75)). The pinned client is `supabase-js@2.78.0` CDN ESM ([poc/web/assets/consent.js](/C:/opendev/code/meta-hackathon/poc/web/assets/consent.js:5)); whether that bundle exposes the email-OTP methods, and their exact shapes, is not established by any repo artifact and was not verified in this step (see Open Questions).

Approve/deny disable both buttons, call the corresponding OAuth method, and follow the returned `redirect_url`; denial therefore yields an OAuth `error=access_denied` redirect with no code and no token exchange (proven live in ticket 3, [poc/README.md](/C:/opendev/code/meta-hackathon/poc/README.md:171)).
- Failure behavior today: a failed password sign-in neither approves nor denies and leaves the form available for retry ([poc/web/assets/consent.js](/C:/opendev/code/meta-hackathon/poc/web/assets/consent.js:78)). There is no code-entry, code-expiry, or resend state of any kind.

### MCP server authentication and authorization (current: Supabase user ID)

- Entry: [poc/mcp-server/supabase/functions/mcp/index.ts](/C:/opendev/code/meta-hackathon/poc/mcp-server/supabase/functions/mcp/index.ts:38) composes `pipeline([withOAuthProtectedResource(), withSupabase({ auth: "user" })], ...)`; unauthenticated requests are rejected with HTTP 401 plus a `WWW-Authenticate` protected-resource challenge before the handler, and parseable unauthenticated `tools/call` requests are logged with `error_code: "unauthenticated"` by the `withUnauthenticatedLogging` wrapper ([poc/mcp-server/supabase/functions/mcp/index.ts](/C:/opendev/code/meta-hackathon/poc/mcp-server/supabase/functions/mcp/index.ts:105)). Arguments and tokens are never logged.
- Identity: inside the handler the server calls `supabase.auth.getUser()` and keeps only `data.user.id` ([poc/mcp-server/supabase/functions/mcp/index.ts](/C:/opendev/code/meta-hackathon/poc/mcp-server/supabase/functions/mcp/index.ts:42)). The user's email is not read, normalized, stored, or logged anywhere in the function. A null ID yields the `unauthenticated` payload per tool ([poc/mcp-server/supabase/functions/mcp/index.ts](/C:/opendev/code/meta-hackathon/poc/mcp-server/supabase/functions/mcp/index.ts:45)).
- Authorization: the captured user ID is passed verbatim as `userId` to `handleListApps`, `handleGetPack`, and `handleCallOperation` ([poc/mcp-server/supabase/functions/mcp/core.ts](/C:/opendev/code/meta-hackathon/poc/mcp-server/supabase/functions/mcp/core.ts:227)). Membership is an explicit query in the service-role data layer: `listMemberApps` selects `poc_app_memberships` rows `WHERE user_id = <Supabase user ID>` ([poc/mcp-server/supabase/functions/mcp/data.ts](/C:/opendev/code/meta-hackathon/poc/mcp-server/supabase/functions/mcp/data.ts:21)), and `isMember` matches on `(app_id, user_id)` ([poc/mcp-server/supabase/functions/mcp/data.ts](/C:/opendev/code/meta-hackathon/poc/mcp-server/supabase/functions/mcp/data.ts:38)). The data layer uses a privileged (service-role) client built per request from `SUPABASE_URL` / `SUPABASE_SERVICE_ROLE_KEY` env ([poc/mcp-server/supabase/functions/mcp/index.ts](/C:/opendev/code/meta-hackathon/poc/mcp-server/supabase/functions/mcp/index.ts:24)); all six fixture tables have RLS enabled with no policies, so this explicit check is the only authorization gate.
- No tool accepts an email: `list_apps` takes an empty object, `get_pack` takes only `pack_id`, and `call_operation` takes only `app_id` / `environment` / `app_version` / `operation` / `arguments` ([poc/mcp-server/supabase/functions/mcp/index.ts](/C:/opendev/code/meta-hackathon/poc/mcp-server/supabase/functions/mcp/index.ts:54)). `validateArguments` rejects any argument not declared by the stored operation definition ([poc/mcp-server/supabase/functions/mcp/core.ts](/C:/opendev/code/meta-hackathon/poc/mcp-server/supabase/functions/mcp/core.ts:106)), so an email smuggled inside `call_operation.arguments` for `list_items`/`add_item` is rejected as `invalid_arguments` today. This is the current, incidental form of the ticket's "email in tool arguments is never identity evidence" property; identity itself comes only from the verified token.
- Tool contracts (the preserved fixture): exactly three tools with unchanged names/inputs/outputs; error taxonomy includes `unauthenticated`, `not_member`, `stale_version`, `invalid_arguments`, `unknown_app`, `unknown_pack`, `unknown_operation`, `invalid_definition`, `item_not_found`, `internal_error` ([poc/mcp-server/supabase/functions/mcp/core.ts](/C:/opendev/code/meta-hackathon/poc/mcp-server/supabase/functions/mcp/core.ts:60)). `handleGetPack` returns Build/Run packs to any signed-in user but requires membership for the grocery app pack; `handleCallOperation` checks membership before version, arguments, or effects, and executes via the stored definition's declarative `effect` descriptors with no operation-name dispatch.
- Logging: every handled call writes a `poc_tool_call_log` row keyed by `user_id` (the Supabase UUID, or null for unauthenticated rejections) via `shapeLogRow` / `safeInsertLog` ([poc/mcp-server/supabase/functions/mcp/core.ts](/C:/opendev/code/meta-hackathon/poc/mcp-server/supabase/functions/mcp/core.ts:67)); the log schema has no token, credential, or raw-argument columns by construction.

## Open Questions

Matters for planning to resolve; none blocks completion of this research.

1. **Internal account ID type and format.** The ticket requires "a permanent internal account ID" but never specifies its type. `poc_app_memberships.user_id` and `poc_tool_call_log.user_id` are both `uuid` columns; a non-UUID account ID cannot be stored in either without a schema change. Planning must settle the ID type and what the tool-call log records as the authorizing identity.
2. **Where resolution happens.** Today the first (and only) identity touchpoint is the MCP handler reading `getUser().id` per request. The ticket requires the account to exist "by the time their first authenticated tool call completes", and sign-in happens earlier on the consent page. The repo contains no account-resolution code at any point in the flow; which component(s) resolve/create accounts, and how the consent page and MCP function share that behavior, is undetermined by repo evidence.
3. **Email source and verification semantics.** The MCP function currently discards everything about the verified user except `id`. What the hosted project's tokens/sessions actually carry (email presence, verified/confirmed state for OTP-created users), and how a first-sign-in email-code flow creates the Supabase user (no separate signup exists today), is not established by any repo artifact.
4. **OTP client API on the pinned bundle.** No OTP method appears in the repo, and the 2.78.0 bundle was verified only for the `auth.oauth` namespace. Whether the email-code request/verify methods exist in that exact pinned bundle, under what names/signatures, and whether first-time emails are auto-created by that flow needs the same kind of verification the OAuth APIs received.
5. **Hosted Auth configuration state.** Email sign-in/OTP enablement, code lifetime, and rate limits on the Loomspan Testing project are dashboard-only facts, unrecorded in the repo and unreadable from this checkout. The ticket fixes the intended end state (built-in sending, default lifetime/limits) but the current hosted state is unknown.
6. **Owner carry-over mechanics against live state.** The hosted membership row points at the synthetic owner's UUID; the designated owner account will not exist until that mailbox first signs in. How the membership reaches that account (and how its correctness is proven without recording the address anywhere) is an execution-time question the repo cannot answer in advance; the env-only designation constraint rules out any committed mapping.
7. **Concurrency proof venue.** The ticket requires racing duplicate first resolutions and observing one account. The current test doubles (`FakeRepo`) and local-Postgres fixture harness model no accounts at all, so neither the unit nor the SQL harness yet offers a place where that race is observable.
8. **Log identity continuity.** Historical `poc_tool_call_log` rows are keyed by Supabase UUID. Whether new rows key by internal account ID (and what happens to comparability with Gate 1 evidence) follows from question 1 and is unrecorded.
