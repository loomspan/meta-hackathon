# MCP Server Gate 1 Tools Research

## Research Question

For ticket `2026-10-27-02-poc-mcp-server-gate1-tools` (ticket 2 of 4 for Gate 1), what does the checked-out repository actually establish about the runtime this ticket must create — one self-built MCP server as one Supabase Edge Function in `poc/mcp-server/` over Streamable HTTP at `https://yjrwyfkybszlpufsflan.supabase.co/functions/v1/mcp`, exposing exactly `list_apps`, `get_pack`, and `call_operation`, authenticated as the signed-in Supabase user, with server-side membership, validation, and version enforcement, DB-driven operation execution, structured errors, and a credential-free tool-call log — given the already-implemented foundation fixture (ticket `2026-10-27-01`)?

No live external service was contacted for project state during this research. The hosted Loomspan Testing project (dashboard, Auth endpoints, database, Edge Functions) was not queried, deployed to, or verified. One official Supabase documentation page was fetched (see Dependencies). Local verification was limited to the foundation ticket's committed Node tests, re-run in this step.

## Summary

There is no MCP server yet. The Edge Function location reserved by ticket 1 contains only an empty placeholder (`poc/mcp-server/supabase/functions/mcp/.gitkeep`), `poc/web/` contains only a placeholder, and a content search over `poc/` finds no MCP, tool-name, transport, or auth code anywhere. Everything this ticket requires — the three tools, authentication, membership enforcement, the generic executor, stale-version semantics, structured errors, and log writes — is currently a *requirement stated in the ticket and governing plan*, not implemented behavior.

What does exist, and what this ticket builds directly on, is the ticket-1 persisted fixture, verified present at the current commit: six `poc_*` tables with RLS enabled and no policies, a JSONB app-definition document for `grocery-list` v1 storing `list_items`/`add_item` with argument definitions, three independently retrievable pack rows (`build`, `run`, `grocery-list`, all version 1), one placeholder owner-membership row, three synthetic items in deliberately non-alphabetical insertion order (Oats/2, Apples/4, Milk/1), and an empty tool-call log table whose nullable columns can represent rejected and unauthenticated calls. The foundation tests (12 Node tests) pass at the current commit; the SQL assertions exist but were not re-run in this step (they require a Docker Postgres run per `poc/README.md`).

Three facts bound this ticket tightly. First, the foundation's preflight is still **NOT VERIFIED — developer dashboard action required** for all three items (OAuth 2.1 server, dynamic client registration, asymmetric JWT signing), and the hosted membership row still points at the placeholder UUID, so no authenticated hosted call can currently be evidenced; the ticket explicitly permits verification with tokens obtained through Supabase Auth directly, and ticket 3 owns the real companion OAuth/consent proof. Second, RLS is enabled on all six tables with **no policies**, so a user-scoped (RLS-bound) database client would currently read and write nothing; the ticket permits "RLS and/or explicit membership checks", and which mechanism the function uses is undecided in repo evidence. Third, the stored definition document describes operations only by `name`, `kind` (`read`/`write`), `description`, and `arguments` — it contains no table, handler, or SQL mapping — so how a future DB-only `remove_item` definition (ticket 4) becomes executable by an unchanged server is not determined by any committed artifact and is the ticket's stated reassessment trigger area.
