## Resolved Decisions (from research Open Questions)
Each research Open Question (§Open Questions 1–7) is settled here or assigned to a Phase 0 inspection gate. Step 4 does not re-derive these.

### D1 — `supabase-js` delivery: pinned CDN ES module, no bundler (research Q3)
The consent glue imports `createClient` from a pinned CDN ES module, e.g. `https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2.78.0/+esm` — Step 4 pins the exact current `2.x` version at implementation time (2.78.0 is the first verified release containing the `auth.oauth` consent APIs; earlier pins such as 2.57.4 lack them) and records it in `poc/README.md` and a comment at the import site. Rationale: the repo has no `package.json`/bundler anywhere and the Edge Function precedent is inline specifiers; a vendored bundle would add a large unreviewable file and a manual update path; a bundler would add tooling the manual-copy deployment must then reproduce. The CDN URL is absolute, so the `/poc/` base path cannot break it. If the CDN import fails at runtime, the page shows a visible load error and the failure is recorded per ticket `:21` (it is not silently worked around). All first-party assets (CSS, `consent-core.mjs`, glue, `config.js`) use relative paths so they resolve under `/poc/` on both the deployed site and the local test server.

### D2 — Sign-in lives inline on the consent page (research Q4)
No separate login route. The consent page states, in order: (a) parse `authorization_id` from `window.location.search`; missing/empty → visible error state, no buttons enabled, stop. (b) `supabase.auth.getSession()` (falling back to `getUser()` semantics via the client) — if a session exists, load details. (c) If no session, show an email/password form calling `supabase.auth.signInWithPassword({ email, password })`; on success load details without any navigation, so `authorization_id` (still in the URL and in a module-level constant) trivially survives sign-in, including across a page reload before sign-in. Rationale: the ticket names exactly two pages; a redirect-to-login round trip is the only place the id could be lost, and the docs require preservation, not a separate route. Passwords are never stored, logged, or placed in the URL; the form is `autocomplete="current-password"` and clears the password field after the call.

### D3 — Anon key via copy-time config injection; never committed (research Q2)
`poc/web/assets/config.js` is committed with placeholder globals only:
```js
window.LOOMSPAN_SUPABASE_URL = "https://yjrwyfkybszlpufsflan.supabase.co";
window.LOOMSPAN_SUPABASE_ANON_KEY = "__LOOMSPAN_ANON_KEY__"; // replaced only in the loomspan.ai copy
```
The Supabase URL is public and already recorded in `poc/README.md`, so it may be committed. The key value is **never** committed in this repo: the legacy anon key is JWT-shaped and would fail [secret-scan.test.mjs](/C:/opendev/code/meta-hackathon/poc/mcp-server/tests/secret-scan.test.mjs:35), and research establishes the value exists nowhere in the repo by design. During the Phase 4 manual copy, the developer replaces `__LOOMSPAN_ANON_KEY__` in the **copied** `config.js` (in the `loomspan.ai` repo) with the public anon/publishable key from the dashboard (Authentication → API Keys), and Phase 4 verifies the placeholder is absent from the deployed output and the service-role patterns are absent from every deployed file (D6). The consent glue fails closed: if the key still equals the placeholder, it renders a configuration error and never constructs a client. If the project offers a non-JWT `sb_publishable_...` key, Step 4 may instead commit that publishable value directly (it cannot trip the JWT regex) — but only after running the secret-scan suite to prove it, and the choice is recorded in `poc/README.md`. Default remains copy-time injection.

### D4 — Consent logic split: pure core + browser glue (enables Node tests)
- `poc/web/assets/consent-core.mjs` — no imports, no DOM, no network. Exports: `parseAuthorizationId(search)` → trimmed string or `null`; `isRedirectOnly(details)` → `true` when the value has `redirect_url` and no `authorization_id`; `formatScopes(scope)` → array of scope strings (`""`/missing → `[]`); `describeAuthorization(details)` → `{ clientName, clientUri, redirectUri, scopes, userEmail }` with `Unknown client` / empty fallbacks; `loadAuthorization(supabase, authorizationId)` → calls `supabase.auth.oauth.getAuthorizationDetails(authorizationId)` and returns a discriminated result `{ kind: "details", details } | { kind: "redirect", redirectUrl } | { kind: "error", message }`; `decideAuthorization(supabase, authorizationId, action)` where `action` is `"approve"` or `"deny"` → calls `approveAuthorization`/`denyAuthorization` and returns `{ kind: "redirect", redirectUrl } | { kind: "error", message }`. Session-missing and other `{ error }` results map to `kind:"error"` with a non-sensitive message (error name/message only, never the request or any token).
- `poc/web/assets/consent.js` — browser glue only: imports `createClient` (D1) and the core, builds the client from `window.LOOMSPAN_SUPABASE_URL`/`LOOMSPAN_SUPABASE_ANON_KEY` (D3 fail-closed check first), wires DOM states (loading / sign-in / details / deciding / error), and performs redirects with `window.location.assign(redirectUrl)`. It calls `decideAuthorization` **without** `skipBrowserRedirect`, then also assigns the returned `redirectUrl` if the library has not already navigated (assigning the same URL twice is harmless; this covers both the library's auto-redirect and the docs' manual-redirect example). Buttons are disabled while a decision is in flight to prevent double submission.
- Consent page states must render, before any decision: requesting client name, requested scopes as a plain list, the signed-in user's email when available, and Approve/Deny buttons. Raw `authorization_id`, tokens, and codes are never rendered or logged.

### D7 — Reference-flow client: hand-rolled DCR + PKCE script (research Q7)
Phase 5 adds `poc/web/tests/oauth-reference-flow.mjs` (developer-run, excluded from the automated `node --test` gates). It reuses the transport pattern of [hosted-acceptance.mjs](/C:/opendev/code/meta-hackathon/poc/mcp-server/tests/hosted-acceptance.mjs:38) (JSON-RPC POST, `Accept: application/json, text/event-stream`, `Mcp-Session-Id` capture/resend, SSE `data:` parsing, `structuredContent` first) and replaces password-grant token acquisition with the real consent path:
1. GET the authorization-server discovery document; assert `authorization_endpoint`, `token_endpoint`, `registration_endpoint` are present.
2. DCR: POST `registration_endpoint` with `client_name: "loomspan-poc-reference"`, `redirect_uris: ["http://127.0.0.1:8765/callback"]`, `grant_types: ["authorization_code"]`, `response_types: ["code"]`, `token_endpoint_auth_method: "none"`; keep `client_id` in memory only (a `client_id` is not a secret, but it is still not recorded in the repo).
3. PKCE: generate `code_verifier` (43–128 chars, `crypto.randomBytes`), `code_challenge = base64url(SHA256(verifier))`, `code_challenge_method=S256`; build the authorize URL with `response_type=code`, `client_id`, `redirect_uri`, `scope=openid email profile`, and a random `state`.
4. Start a one-shot local HTTP listener on `127.0.0.1:8765/callback`; print only the authorize URL and instruct the developer to open it, sign in on the deployed consent page as the test owner, and Approve (approval run) — the listener validates `state`, captures `code` in memory, and never prints `code`, `state`, or `verifier`.
5. Token exchange: POST `token_endpoint` form-encoded `grant_type=authorization_code&code&redirect_uri&code_verifier&client_id`; assert an `access_token` was returned (print only "token received", its `token_type`, and `expires_in` if present).
6. MCP: `initialize` then `tools/call list_apps` with the OAuth token; assert `ok:true` and (owner) exactly the `grocery-list` summary without `instructions`/`operations`; print only tool name, `ok`, app IDs, HTTP statuses.
Denial run (`--deny` flag or second invocation): use a **fresh DCR client** (new `client_id` ⇒ no prior grant, so a real consent decision is forced; see D8), instruct the developer to Deny, assert the callback receives `error=access_denied` with matching `state`, assert no code is present, skip token exchange, and assert an unauthenticated `tools/call list_apps` against the MCP endpoint returns HTTP 401. Exit code is non-zero on the first failed assertion; every printed line is redacted by construction (no URL query strings containing `code`/`state`, no headers, no bodies containing tokens).

### D8 — Grant-state management for repeatable tests (research Q6)
Because previously consented `(client, scopes)` pairs auto-approve (redirect-only details), approval and denial evidence must force a fresh decision. The reference script does this by registering a fresh DCR client per run (D7 step 2), which needs no grant-revocation API and no dashboard action. If Step 4 instead tests through a companion-like persistent client, it must first revoke the grant via `supabase.auth.oauth.listGrants()` / `revokeGrant(...)` for that client as the signed-in user, and record that it did so (grant IDs are not recorded). A run that receives the redirect-only response is recorded as "previously consented — auto-approved", not as an approval-decision pass.

## Impact and Risk Analysis
- **Security/authorization (highest):** the consent page is the token-issuance decision point. Mitigations: anon/publishable key only (D3/D6); decisions only after `getAuthorizationDetails` succeeds in a signed-in session (D2/D4); client + scopes rendered before Approve/Deny enable; double-submit disabled; denial path tested live (Phase 5) and must yield no token and a 401 on unauthenticated `list_apps`. OAuth access tokens have full user-data access (research), so a consent bug invalidates Gate 1 — hence the fresh-client denial run (D8).
- **Secret leakage:** three surfaces — committed source (guarded by the existing secret-scan suite; D3 keeps the key out), deployed output (guarded by D6 before push), and evidence/logs (script prints are redacted by construction, D7; `poc/README.md` redaction rule already forbids key/token/credential values). The service-role key's only legitimate home remains the Edge Function env ([index.ts](/C:/opendev/code/meta-hackathon/poc/mcp-server/supabase/functions/mcp/index.ts:24)); nothing in `poc/web/` may import from `poc/mcp-server/`.
- **Base-path breakage:** absolute asset paths (`/assets/...`) would resolve to the loomspan.ai root, not `/poc/`. All first-party references are relative (`assets/...` from `/poc/`, `../assets/...` from `/poc/oauth/`) and the local test server (Phase 3) serves the pages under `/poc/` so this is exercised before deployment.
- **SPA-fallback interception (unverified assumption):** the main site may swallow `/poc/` or `/poc/oauth/consent`. Phase 0 inspects the other repo's routing; Phase 4 proves the live URLs return POC marker content with HTTP 200 and no redirect to the main-site shell. If interception is found, the fix belongs to the `loomspan.ai` repo's routing (e.g. a `/poc/*` static passthrough), recorded in `poc/README.md`; Step 4 must not claim the criterion until the live check passes.
- **Dashboard change side effects:** changing Site URL from `http://localhost:3000` to `https://loomspan.ai` affects every Auth redirect that used the old value; no repo artifact records another consumer (research). Phase 0 records the current values before change so the change is reversible, and `supabase config push` remains forbidden.
- **Already-consented shortcut:** repeat runs may auto-approve and show no decision (D8). Tests that ignore grant state would falsely pass approval/denial; the reference script's fresh-client-per-run design removes the ambiguity.
- **Cross-repo deployment access:** Step 4 may lack the `loomspan.ai` repo locally or push access. That is an escalation gate (Phase 0/4), not a silent skip: without deployment, criteria 1–2 and the live reference flow cannot pass, and Step 4 returns `needs-developer` with the completed local work preserved.
- **Beta external protocol:** Supabase OAuth 2.1 is beta; if live behavior differs materially from the verified `authorization_id` flow, the ticket reassessment trigger fires at that point — Step 4 stops, records the actual required flow with redacted evidence, and returns `needs-developer` rather than building around it.
- **Failure classification:** any discovery/DCR/sign-in/consent/token-exchange failure is recorded as authentication/integration failure, cause unconfirmed, with step + redacted evidence + workaround/burden (Phase 6 template). MCP/schema defects route back to tickets 1–2.

## Implementation Approach
Plain static files, no build step, matching the repo's "no web tooling anywhere" state and the manual-copy deployment: what is in `poc/web/` (minus `tests/`) is byte-for-byte what is copied to `loomspan.ai`, so local verification predicts deployed behavior. Logic that needs tests (`parseAuthorizationId`, `isRedirectOnly`, `formatScopes`, `describeAuthorization`, `loadAuthorization`, `decideAuthorization`) lives in the import-free `consent-core.mjs` (D4) so Node can test it directly; the browser glue is kept thin enough that its untested remainder is DOM wiring and redirects, which the Phase 5 live flow then exercises end to end. The onboarding page is static HTML with a copy button (Clipboard API with a selectable-text fallback). Styling is one shared `poc.css`: solid colors, system fonts, left-aligned single column, no gradients/glow/glass, no emoji, no scale-on-hover, transitions gated by `prefers-reduced-motion`. Phases are ordered so nothing live is touched until local proof exists: decide/inspect (0) → build pages (1–2) → local automated proof (3) → dashboard + deploy + live route proof (4) → live OAuth proof (5) → documentation/evidence close-out (6).

## Risks and Rollback/Recovery
